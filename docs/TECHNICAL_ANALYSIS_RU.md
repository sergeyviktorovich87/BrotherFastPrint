# BrotherFastPrint — технический анализ и границы POC

Это исходный анализ этапа POC. С тех пор пользователь подтвердил физическую прямую печать 0.1.2; в 0.2.0 реализованы PrintService и многостраничный preload. Актуальная архитектура и оставшиеся проверки описаны в `PRINT_SERVICE_RU.md`, результаты — в `VALIDATION_RU.md`.

Дата анализа: 1 ноября 2026 года. Цель первой версии — проверить реальную печать одной страницы на Brother HL-L2340DWR по RAW 9100. Системная служба и сравнение многостраничной скорости относятся к следующим этапам, после успешного физического опыта.

## 1. Вывод по осуществимости

Схема Kotlin → PdfRenderer → однобитный растр → JNI/brlaser → TCP технически обоснована. В исходниках brlaser есть профиль HL-L2340D series с идентификатором HBP/URF и duplex. Он является хорошей отправной точкой, но запись модели в списке совместимости ещё не подтверждает работу конкретного HL-L2340DWR, прошивки и Wi-Fi соединения.

Быстрая печать Windows не доказывает, что принтер сам обрабатывает PDF. Подготовку выполняет драйвер на компьютере. Android тоже должен выполнить рендер, перевод в монохромный растр и сжатие. Переносить эти операции «с телефона» без компьютера невозможно; можно организовать их заранее и эффективнее.

Исходная причина пауз пока является гипотезой. Возможны медленный рендер, передача несжатого/неудачно сжатого растра, создание отдельных заданий, Wi-Fi, ограничения буфера и самого механизма принтера. Поэтому успех проекта определяется физическими замерами, а не временем записи в сокет.

## 2. Что действительно нужно от brlaser

Зафиксирован исходник `pdewacht/brlaser`, commit `2a49e3287c70c254e7e3ac9dabe9d6a07218c3fa`. Полный список Git blob SHA находится в `third_party/brlaser/UPSTREAM.json`. Скопированные upstream-файлы не изменены.

| Компонент | Назначение | В APK |
|---|---|---|
| `src/line.cc`, `src/line.h` | Сжатие строки, в том числе относительно предыдущей | Да |
| `src/block.h` | Группировка строк в Brother-блоки | Да |
| `src/job.cc`, `src/job.h` | PJL, параметры страницы, растровый поток, завершение задания | Да |
| `src/main.cc` | CUPS CLI, чтение CUPS raster, сопоставление заголовков | Нет |
| `src/debug.cc`, `src/debug.h` | Диагностика заголовка CUPS | Нет |
| `brlaser.drv.in` | Профили, поля, разрешения, настройки | Референс в исходниках |
| CUPS, Ghostscript, Linux userspace | Не нужны при использовании PdfRenderer | Нет |

Кодировщик принимает строки, где один пиксель занимает один бит: 1 — чёрный, 0 — белый; старший бит идёт первым. Важна нулевая добивка последнего байта строки. Внутри кодировщика используются полосы до 64 строк и блоки менее 16350 байт.

Один объект `job` поддерживает несколько `encode_page()`. Начало задания пишется один раз, конец — в деструкторе. Поэтому для будущего многостраничного режима нужно сохранить один объект на весь документ и закрыть его до окончательного завершения отправки. Пересоздание объекта для каждого листа испортит именно то поведение, которое требуется улучшить.

В POC `encoder.cpp` адаптирует callback чтения строк к файловому дескриптору. Контекст чтения thread-local, проверяются точная длина растра, короткое чтение, ошибки записи, отмена и наличие завершающего EOJ. `bridge.cpp` делает JNI и упаковку полос, а сетевое соединение остаётся в Kotlin.

## 3. Что получает Android PrintService

Контракт `PrintDocumentAdapter.onWrite()` — многостраничный PDF. Фото, HTML и документы офисных приложений сначала преобразует приложение-источник через Android Print Framework. Служба получает документ через `printJob.document.data`, а настройки — через `PrintJobInfo` / `PrintAttributes`.

Особенно важная деталь: в изученном AOSP `PrintDocument.getData()` создаёт `ParcelFileDescriptor.createPipe()`. Поэтому нельзя передавать полученный дескриптор прямо в PdfRenderer: тому нужен seekable FD. Правильный путь — получить документ на главном потоке, полностью скопировать pipe в приватный файл на рабочем потоке и открыть этот файл для PdfRenderer.

Методы PrintService, PrintJob и PrintDocument, для которых это требует API, вызываются на главном потоке. Копирование, рендер, JNI и TCP выполняются вне UI. Для будущей службы необходимо отдельно проверить диапазоны страниц и их соответствие содержимому spool PDF; нельзя вслепую применять диапазон повторно и терять страницы.

В POC вместо Print Framework используется системный выбор PDF (`ACTION_OPEN_DOCUMENT`), затем такая же приватная копия. Проверка фактического дескриптора Android spool будет повторена на Samsung при реализации этапа 3. Сейчас изучен контракт и код AOSP, а не снят spool с телефона пользователя.

## 4. Рендер и память

Выбраны minSdk 26, compileSdk/targetSdk 36, обязательная ABI arm64-v8a. API печати и PdfRenderer доступны раньше; Android 8 выбран как практическая нижняя граница для поддержки. В POC нет Jetpack Compose, WebView, внешних PDF-библиотек и сетевых SDK.

`PdfRenderer.Page.render()` вызывается с `RENDER_MODE_FOR_PRINT`, явно заданной аффинной матрицей и полосой 128 строк. Белый фон очищается перед каждой полосой. Матрица сохраняет масштаб страницы, смещаясь по Y; ориентация landscape поворачивается по часовой стрелке на портретную A4. Большие страницы уменьшаются до A4, маленькие не растягиваются. Пиксели за imageable area обрезаются.

POC повторяет геометрию PPD brlaser: `HWMargins 8 8 8 16` в типографских пунктах, порядок left/bottom/right/top. При A4 600 DPI получается 4827 × 6816 полезных пикселей, 604 байта на однобитную строку. Это не независимое доказательство физического начала координат HBP: его проверяет тестовая рамка на реальном листе. Нельзя просто послать полноразмерный A4 bitmap, игнорируя поля драйвера.

Полоса ARGB занимает примерно 2.36 MiB, её однобитная копия — около 76 KiB. Полный однобитный растр хранится на диске и занимает 4 116 864 байта. Полный ARGB bitmap такого же поля потребовал бы более 125 MiB, поэтому он не создаётся. Ordered Bayer 8×8 сохраняет фазу между полосами и позволяет печатать серые изображения.

Сам PdfRenderer/PDFium может расходовать дополнительную память на шрифты и встроенные изображения. Полосный вывод ограничивает память наших буферов, но не даёт математической гарантии против OOM на произвольном вредоносном PDF. Рендер и кодировщик работают в `isolatedProcess=true`, без разрешений приложения. Они получают только FD исходного PDF, растра и выходного HBP. Падение изолированного процесса не считается успешной подготовкой.

Пределы POC: PDF до 100 MiB, свободное место перед работой не менее 150 MiB, первая страница, A4, 600 DPI, simplex, одна копия, HBP до 16 MiB. Нативные проверки 10/50 страниц используют синтетические данные; это не тест Android с PDF на 50 страниц.

## 5. Выбранный pipeline

Первый физический опыт использует **preload**: копирование PDF → полосный рендер и монохромизация первой страницы → brlaser в файл → одно TCP-соединение → передача готового файла. Это изолирует проблемы HBP и координат от проблем конвейера и исключает ожидание рендера после начала передачи.

Для этапа 2 предусмотрены два сравниваемых режима:

| Режим | Организация | Преимущество | Компромисс |
|---|---|---|---|
| Preload | Все выбранные страницы заранее в одном HBP-файле, затем один TCP job | Убирает зависимость подачи от скорости рендера во время печати | Дольше до первого листа, больше места на диске |
| Streaming | Производитель полос → ограниченная очередь → один native job encoder → очередь сжатых блоков → один TCP sender | Первый лист начинается раньше; подготовка следующих идёт параллельно | При недостаточной скорости подготовки паузы сохранятся |

PdfRenderer с открытой страницей используется последовательно; его нельзя произвольно разделить между тремя потоками. Для streaming понадобится отдельный адаптер native job с безопасным временем жизни и backpressure. Начальная очередь — несколько полос, а не все ARGB-страницы. Запас 2–3 **готовых сжатых страниц** можно хранить ограниченно на диске. Окончательный размер буфера выбирается по замерам.

Просто передать PDF в порт 9100 нельзя. Также нельзя отправлять отдельные самостоятельные HBP jobs и считать их единым заданием. Preload не отменяет ограничения физического принтера: даже при мгновенной подготовке остаются прогрев, duplex и механическая скорость.

## 6. TCP, ошибки и достоверность статусов

POC открывает исходящее соединение к сохранённому локальному IPv4/порту. Адрес по умолчанию 192.168.1.41:9100. DNS и публичные IP не используются. Сокет привязывается к Wi-Fi либо Ethernet, чтобы работа с локальным принтером не зависела от маршрута мобильного интернета/VPN. При отсутствии такой сети выдаётся понятный статус.

`SocketChannel` работает в неблокирующем режиме с `Selector`: connect timeout 5 секунд, две попытки соединения до передачи печатных данных; write idle timeout 15 секунд и общий лимит передачи 120 секунд. `Socket.setSoTimeout()` не применяется в качестве write timeout: он не ограничивает запись.

Повтор разрешён только для открытия соединения. С первой попытки `write()` ошибка становится потенциально неоднозначной, даже если счётчик принятых ОС байтов равен нулю. Автоповтора задания нет. Отмена закрывает канал; данные в буфере принтера могут продолжить печататься. Такое состояние явно показано пользователю.

Запись в сокет и `shutdownOutput()` подтверждают только передачу в сетевой стек. Они не подтверждают выход листа. В POC статус «Online» означает доступный TCP-порт; бумага, тонер и результат физической печати не выдумываются.

Для следующих этапов отдельно исследуются IPP Get-Printer-Attributes и, при необходимости, SNMP/PJL-статусы, фактически поддерживаемые этой моделью. Наличие IPP/mDNS не означает, что принтер принимает произвольный PDF. Если достоверного статуса нет, он остаётся неизвестным. После неопределённой ошибки будущая PrintService не должна оставлять задание в состоянии, которое автоматически повторит документ.

## 7. Discovery, настройки и duplex

Сначала используется ручной IP. Будущая `PrinterDiscoverySession` создаёт стабильный PrinterId для сохранённого устройства, публикует реальные capabilities (A4/600 DPI/mono и только проверенные опции), проверяет доступность асинхронно, прекращает callbacks при уничтожении сессии.

Затем добавляется NsdManager для `_pdl-datastream._tcp`, `_ipp._tcp`, `_ipps._tcp`: обнаружение кандидатов, проверка модели/адреса/возможностей, выбор пользователем. Поле порта из IPP-записи — порт IPP, его нельзя автоматически трактовать как RAW 9100. Потеря mDNS не удаляет ручную запись. Сплошное сканирование подсети не требуется.

В upstream `page_params` есть copies, resolution, duplex boolean, economode, tray, media, paper. Но нет отдельного `tumble`/параметра стороны переплёта; `job.cc` при duplex пишет фиксированную последовательность `ESC&l2S`. Профиль использует `Duplex rotated`, то есть часть подготовки оборота выполняется растровой цепочкой CUPS. При переносе без CUPS эту работу надо воспроизвести и проверить на асимметричных страницах. Оба варианта переплёта нельзя объявлять готовыми только на основании наличия boolean.

Копии тоже требуют проверки collated/uncollated поведения. В системе источником настроек должен быть PrintJobInfo; настройки приложения служат значениями по умолчанию. Качество, DPI и toner save нельзя смешивать в одно неясное поле.

## 8. Разрешения и безопасность

В POC запрошены только `INTERNET` (Android требует его и для локального TCP) и `ACCESS_NETWORK_STATE` для выбора Wi-Fi/Ethernet. Сетевая логика приложения ограничивает назначение локальными IPv4; подключение к интернет-сервисам отсутствует. Входящих сокетов, серверов HTTP, аналитики и API разработчика нет.

В штатной конфигурации Android 14/15 и Android 16 с target 36 для этого RAW-сокета не нужны location, доступ ко всем файлам и разрешения камеры/микрофона. Android 16 имеет opt-in ограничение локальной сети через compat flag `RESTRICT_LOCAL_NETWORK`, временно связанное с `NEARBY_WIFI_DEVICES`. POC этот режим не включает и разрешение заранее не запрашивает. Проверка с принудительно включённым ограничением и соответствующим запросом разрешения — отдельная матрица совместимости. При переходе на target 37 нужно применить официальные правила `ACCESS_LOCAL_NETWORK`/системного выбора устройства; нельзя механически добавить его для target 36.

Все spool-файлы — внутри `noBackupFilesDir/spool`, исключены из облачных backup/device transfer. После любой завершившейся попытки они удаляются; после смерти процесса остатки очищаются при следующем запуске контроллера. После успешного создания HBP исходный документ не загружается никуда, кроме указанного принтера. Удаление файлов не является гарантированным физическим стиранием флеш-памяти.

Лог содержит время, размеры, счётчики страниц, технические коды и IP/порт; он хранится в ограниченной очереди в памяти. Название PDF, его текст, URI, изображения и имена пользователей не записываются. Копирование лога в буфер выполняется только кнопкой пользователя.

RAW 9100 передаёт данные без шифрования. Это выбранный пользователем локальный транспорт, подходящий для доверенной LAN, но не средство защиты документа от участника этой сети. `usesCleartextTraffic=false` относится к поддерживающим эту политику HTTP-стекам и не превращает RAW в TLS.

Для современных Android native-библиотека собирается NDK r28c с выравниванием ELF на 16 KiB. Проверяются также ZIP alignment и ABI. Версии инструментов закреплены; это делает сборку повторяемой по процедуре. Побитная идентичность APK требует отдельного контроля времени, метаданных и постоянного ключа подписи; debug APK этого не обещает.

## 9. Лицензия и коммерческое использование

brlaser распространяется под GPL-2.0-or-later, а не MIT/Apache. Для приложения выбрана GPL-3.0-or-later; разрешённый upstream переход на GPLv3 обеспечивает совместимость с Kotlin runtime под Apache-2.0. Исходники, тексты лицензий и закреплённые версии включены в поставку. Коммерческое распространение допустимо при соблюдении лицензии, включая предоставление соответствующих исходников получателям бинарной версии. JNI не является автоматическим способом сделать производную сборку закрытой. Если понадобится закрытый продукт, модель распространения и драйвер нужно пересмотреть до релиза. Основание по совместимости: [GNU license list](https://www.gnu.org/licenses/license-list.html), [GNU FAQ о GPLv2-or-later](https://www.gnu.org/licenses/gpl-faq.en.html#v2v3Compatibility).

AndroidCupsPrint изучен как пример жизненного цикла PrintService, но его CUPS/IPP-клиент сам по себе не преобразует PDF в Brother HBP. Mopria CUPS-for-Android содержит большую библиотеку CUPS со своим HTTP/IPP/TLS/raster стеком. Для узкого RAW/brlaser POC она не нужна. Код обоих проектов в приложение не переносился.

## 11. Проверяемые этапы и критерии перехода

1. **POC:** установить APK, проверить TCP, создать тестовую A4, напечатать страницу 1, проверить ориентацию, рамку и линейку; затем проверить первую страницу собственного PDF. Успех — физически правильный лист.
2. **Многостраничная печать:** 1/10/50 страниц, один native job и один TCP socket, preload/streaming, память и место на диске, отмена и разрыв связи, отсутствие автодубликатов.
3. **PrintService:** появление в системной печати Samsung; работа с PDF/браузером/галереей/Office; диапазоны, lifecycle, повторное подключение, статусы без ложных подтверждений.
4. **Возможности:** discovery, duplex long/short edge, копии, бумага, качество и диагностика. Для duplex обязательны тесты чётного/нечётного числа страниц и обоих переплётов.
5. **Скорость:** один и тот же PDF и настройки в стандартной службе Android, Brother iPrint&Scan, BrotherFastPrint preload/streaming и, как референс, Windows. Одинаковые Wi-Fi, бумага, DPI и simplex/duplex; холодный и прогретый запуск измеряются отдельно.

В логе измеряются получение задания, копирование, начало/конец рендера и конвертации, объём HBP, начало/конец TCP и общая длительность обработки. Физические времена выхода листов измеряются видео/наблюдением: лог RAW их не содержит. Сравниваются первый лист, общая длительность, интервалы между листами и длинные остановки, хотя бы три прогона каждого режима. Если preload не уменьшает паузы, искать ограничение принтера/передачи/формата, а не объявлять конвейер успехом.
