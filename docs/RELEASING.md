# Публикация проверенного APK

Релиз 0.3.2 содержит APK, который владелец уже проверил на телефоне. Этот файл не пересобирается в CI: новая debug-подпись не обновила бы установленную Preview. Ключ хранится отдельно от репозитория и не передаётся GitHub Actions.

## Подготовка сопровождающим

1. Проверить APK на устройстве, подпись через `apksigner verify --print-certs`, alignment и SHA-256. Зафиксировать результат, версию, ограничения тестирования и метаданные в `docs/releases/<tag>.json` и `<tag>.md`. Не добавлять ключ в git.
2. Закоммитить соответствующий исходный код и документацию; отправить `main`. Рабочее дерево должно быть чистым.
3. Проверить файл без отправки: `python3 tools/stage_release.py v0.3.2-preview /path/to/tested.apk`.
4. Передать проверенный файл во временную orphan-ветку: `python3 tools/stage_release.py v0.3.2-preview /path/to/tested.apk --push`. Скрипт сверяет хеш/размер, привязывает файл к текущему commit и не перезаписывает существующую ветку.
5. Создать аннотированный тег на этом commit и отправить его: `git tag -a v0.3.2-preview -m 'BrotherFastPrint 0.3.2 Preview'`, затем `git push origin v0.3.2-preview`.

Альтернатива для публикации через GitHub API/connector: после передачи тех же двух staging-файлов создайте временную ветку `release/v0.3.2-preview` на commit исходников. Её CI выполняет проверки, создаёт аннотированный тег, публикует релиз и удаляет временные ветки с точными leases. Уже существующий тег с другим commit не перемещается.

## Что делает GitHub Actions

Сначала выполняются те же native/JVM/lint/build проверки, что для `main`. Только workflow доверенного push тега или явной ветки `release/v…` получает `contents: write` для публикации. Pull requests этого разрешения не получают. Actions закреплены по полным commit SHA.

Publisher проверяет соответствие тега, исходного commit, staging manifest и закреплённого SHA-256 APK. Он создаёт draft prerelease, добавляет проверенный APK, исходники из того же git commit, метаданные и `SHA256SUMS`. После обратного скачивания и проверки всех файлов draft публикуется. Существующие файлы с другими хешами не перезаписываются. Успешно использованная временная ветка удаляется с проверкой её точного commit.

Если CI не прошёл, тег не означает опубликованный APK. Исправьте причину и повторите failed jobs для того же commit либо подготовьте новый тег; не перемещайте уже опубликованные теги. Staging APK уже публичен после отправки ветки; документы и приватные ключи передавать этим способом нельзя.

Для восстановления незавершённой публикации ветка `release/v…` может продвинуться поверх тега только с изменениями publisher, workflow и этой инструкции. Скрипт проверяет ancestry и точный список путей; приложение, зависимости, метаданные и остальные исходники должны совпадать с замороженным тегом. Архив и staging manifest по-прежнему относятся к исходному тегу, временная ветка удаляется с lease на фактически запущенный commit. Черновик ищется в авторизованном списке релизов и читается по числовому ID; tag endpoint не используется для получения draft.

## Подпись и воспроизводимость

Исходники, Gradle Wrapper, версии SDK/NDK и upstream brlaser закреплены. `assembleDebug` создаёт APK с локальным debug-ключом; CI использует временный ключ runner. Такой APK отличается от проверенного релиза и не устанавливается поверх него как обновление. Для будущих пользовательских обновлений нужен сохранённый исходный ключ; он не должен попадать в Issues, git или source ZIP.

Соответствующий source ZIP и тег содержат полные исходники приложения, JNI/brlaser, тесты, лицензии и инструкции сборки. Зависимости сборки загружаются обычными SDK/Gradle-инструментами. Побайтовая идентичность APK между средами не обещается.
